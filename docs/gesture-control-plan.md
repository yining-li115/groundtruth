## 1 · 核对结果

### 1.1 📏 手离开后，相机继续飞 1221 毫秒

v1 §8 末尾提到"飞行不可沿旧速度持续 1.2s"。**成立，且比推测更确定。**

根因（三处代码合起来才成立，任何一处单看都无异常）：

1. `HandControl.tsx` 的飞行分支门控在 `s.present`：`if (!store.entered && s.present) steer(s.x, s.y, …)`。
2. `DEFAULT_POINTER.leaveMs = 1200`——手消失后 `present` 还要保持 1.2 秒才落下。
3. `HandPointer.update` 的位置只在 `if (palm && box)` 里写入。手没了，`s.x/s.y` 就**冻在最后一帧**。

于是 `steer()` 被继续以陈旧坐标调用，`latch()` 持续返回同一个方向，相机以满速继续飞，直到 `present` 落下才 `stopFlight()`。

复现（复用 `scripts/check-pointer.ts` 的合成手骨架，30fps 虚拟时钟）：

```
hand present, held to one side:      yaw=1  present=true
after the hand vanishes:             yaw kept non-zero for 1221ms
final:                               yaw=0  present=false
```

这是**最该先修的一条**，因为它在现场表现为"我手都放下了，画面还在自己转"——和"没识别到我"是同一种观感，却是完全不同的病。

**修法**：存在状态与动作状态分离。光标可以保留 1.2 秒（防闪烁，这是它存在的理由），但**飞行意图必须在第一个没有手的视觉帧上归零**。即：`steer()` 的调用条件改为"这一帧有手"，而不是"访客还算在场"。

### 1.2 ✅ v1 §3 的三条应用层故障，全部属实

| 故障 | 位置 | 确认 |
|---|---|---|
| `hands[0]` 无稳定归属 | `mediapipe.ts` `allHands()` | 按 MediaPipe 返回顺序原样透出，未做任何排序或轨迹匹配。旁人的手或访客的第二只手可以在帧之间夺走 index 0 |
| 硬编码 1280 | `handPointer.ts` `confidence(face, box, palmNorm * 1280)` | 属实，且源码里已有注释标记为审计发现、故意未改 |
| 无解码帧仍报 running | `useHandPointer` / `handStatus` | 属实。track 报 `live` 且 `getSettings()` 给出自信的 1280×720，而 `videoWidth` 是 0，循环正确跳过，状态仍是 `running` |

### 1.3 ✅ 按帧计数的常数清单

v1 说"2 帧、8 帧随帧率改变语义"，属实。完整清单（这三个是全部）：

| 常数 | 值 | 在 30fps 下 | 在 15fps 下 |
|---|---|---|---|
| `FistLatch` on/off | 2 / 3 帧 | 66 / 100 ms | 133 / 200 ms |
| `PinchDetector.settleFrames` | 8 帧 | 265 ms | 533 ms |
| `PinchDetector.graceFrames` | 5 帧 | 165 ms | 333 ms |

而 `PRESS_DEBOUNCE_MS`、`MAX_HOLD_MS`、`pressFreezeMs`、`enterMs`、`leaveMs` 已经是毫秒。**混用是隐患**：掉帧时，用毫秒的那半套不变，用帧数的这半套时长翻倍，两者的相对关系——尤其 `settleFrames` 与 `PRESS_DEBOUNCE_MS`——会悄悄反转。改成毫秒，代价接近零。

### 1.4 ⚠️ 生产链路目前只有两个自由度

v1 §1 把"三轴平移 + 环顾"写成第一版目标，读起来像是在改进现有的平移。**现有链路没有平移。**

`flightInput.ts` 的 `steer()` 只写 `yaw`（左右转）和 `dolly`（前后），**从不写 `strafe` 和 `lift`**——那两个字段只有 `useHandFlight.ts` 会写，而它只在 `/?exp=spark` 开发页跑，还自开摄像头。

所以现状是：**握持中的访客能做的只有"转"和"前后"**。这不改变 v1 的方向，但改变优先级——平移是新功能，排在"先让转向不难受"和"先修 P0"之后。

### 1.5 ⚠️ Spark 控制器：借参数，不借实现

`node_modules/@sparkjsdev/spark/dist/types/controls.d.ts` 确认 `PointerControls` 暴露：

```ts
rotateSpeed  slideSpeed  scrollSpeed  moveInertia  rotateInertia
rotateVelocity: THREE.Vector3   moveVelocity: THREE.Vector3
pressMoveDelayMs  pressMoveAccelMs  pressMoveSpeed  …
```

即 v1 R2 描述的能力确实存在。**但**：整个类由绑在 canvas 上的 `pointerdown/pointermove/pointerup` 驱动，状态是 `PointerState { initial, last, position, pointerId, … }`。要用它，只能把手的位置合成为 PointerEvent 派发到 canvas——这会把飞行控制绑死在 DOM 事件上，绕过我们现有的抓取会话，并且**再也无法离线测试**（本仓库 78 条 pointer 测试的全部价值就在于不需要浏览器）。

我们自己那份（`SparkCampusExperiment.tsx` 的 `manual` 块）已经在做同样的事，而且有一个 Spark 没有的关键性质：**位移是相对冻结基准姿态算的**（`basePos`/`baseQuat`，每帧从基准重推而不是累加上一帧），所以不会漂移。v1 §6.2 "更稳妥的实现"说的正是这个——**它已经存在了**，只是目前喂给它的是量化后的 −1/0/+1，而不是连续位移。

**结论**：把 `rotateInertia`/`moveInertia` 当作参数形状与命名的参考，实现留在自己这边。

### 1.6 🆕 约一半的推理花在重复帧上

v1 §8 说"只推理新解码的视频帧"。核对下来这不只是优化，是**现状就在浪费**：

`useHandPointer` 的循环挂在 `requestAnimationFrame`（≈60Hz），除了 `video.readyState < 2` 之外**没有任何一处检查这一帧是不是新解码的**，每次都照跑 `engine.process(video, ts)`；而摄像头只以 ~30fps 解码。代码里的 `if (ts <= lastTs) ts = lastTs + 1` 是为满足 MediaPipe"时间戳必须严格递增"的要求，它保证了调用不会因为时间戳相同被拒绝——但它不认识"同一张画面"，所以同一帧会被当成两帧各跑一遍两个模型。

同一帧上还跑着 `FaceDetector`（人脸在这里只当尺子用，5–10Hz 足够）和 `numHands: 2`（下游只读 `hands[0]`）。

**修法**：改用 `video.requestVideoFrameCallback` 驱动推理（每个解码帧恰好一次），人脸降频，`numHands` 在确定归属方案前保留 2（它是识别"旁边还有人"的唯一来源）。渲染循环照旧 60Hz 读状态。预期直接省掉约一半的视觉计算——这块 GPU 是和高斯渲染抢的。

### 1.7 ✅ 外部引用核实结果

  - ⚠️ **v1 漏了一条**：它用的是**旧版 MediaPipe Hands / FaceMesh solutions**，不是我们用的 `tasks-vision` Task API。两者的 landmark 语义相近但 API、置信度含义和 world-landmark 支持不同，**照抄阈值无效**。

## 2 · 交互语法（修订）

共同语义不变：**张手指向；握拳抓住；移动手操作；张手结束。**

### 2.1 ⚠️ 无人 / 刚进入：换手段，不换目的

v1 §4.1 提议"不因为手出现就开始飞行"。这**反转了一条写在 `ShowreelFlight.tsx` 注释里的明确决策**：

> The tour hands the camera over as soon as a hand is seen — not once some grip is discovered. A screen that keeps playing its own loop while somebody is standing in front of it waving reads as a screen that cannot see them.

那条决策的**目的**是：路人必须立刻知道屏幕看见了他。它的**手段**是：立刻把相机交出去。手段之所以被选中，是因为当时除了"相机动起来"以外没有别的反馈通道。

取消位置转向之后，反馈通道有了——光标出现、提示出现。**目的照旧成立，手段可以换。**

采用 v1 的行为，但附一条硬要求：**必须同时改掉 `ShowreelFlight.tsx` 里那段注释**，写明"原决策的目的由光标与提示承担；相机只在明确抓取时才离开导览"。否则下一个读到那段注释的人（包括未来的我）会把它改回去，而且理由充分。

### 2.2 场景环顾 LOOK（v1 版核心，唯一必做的相机改动）

在非 UI 的场景背景上握拳 → 记录抓取时的手位置、当前相机姿态、归一化尺度、手的归属。握拳移动产生 yaw / pitch 增量；手停则画面停。张手结束，回位时不操控场景；再握拳可继续累积，转满 360° 无限制。

**关于"握拳左右扇"**（导师原话）——v1 §4.2 的判断是对的，且必须写清楚，因为它和导师的直觉正好差一层：

> 持续握拳左右往返，就应该产生左右往返的画面。系统无法可靠猜出其中哪一次是"无效回位"。

想要"扇一下、画面顺势转过去"，正确的做法不是让系统去猜，而是**回位时张开手**：

```
握拳 → 向右扫 → 张手（画面顺势继续转一点，平滑停住）→ 手放回左边（张着，什么都不发生）→ 再握拳 → 再扫
```

这恰好也是"抽搐"问题的根治：以前来回扇会抽，是因为**位置当方向**——手在中心右边就一直发"右"，越过死区回到左边就一直发"左"，一次往返就是一串正负交替指令，外加每次穿越死区边界的抖动。改成位移驱动后，握拳段是 1:1 跟手（本来就不匀速，顺带解决"匀速"那条），张手段完全无输入。

其余照 v1：默认采用"抓住场景拖动"的方向，用少量陌生用户测反向需求；镜像只能有一处（现在在 `calibration.mapToBox`，**不许再加第二处**）；锁 roll；pitch 在接近上下极点处限位。

⚠️ 补一条 v1 没有的限位理由：现在的五个导览停靠点是**逐帧验证过"模型填满画面、不露空"**的（`scripts/build-tour.py` 的填充率门槛 ~99%，`tour.json` 里 5 个 stop 的 `fill` 为 1.0 / 1.0 / 1.0 / 0.996 / 1.0）。手一旦能自由抬头，这个保证立刻失效。所以 pitch 限位在天空背景落地（另一项任务）之前**必须收紧**，之后可以放开。

### 2.3 ❌ 移动区：v1 版删除，移入 v2

v1 §4.3/4.4 提议底部中央放一个移动区、右下放一个高度区。**与现有版面正面冲突**：

- 底部中央是 **Enter 按钮 + 手势说明**（`showreelFlight.css`：`.sf-enter { bottom: 3rem }`、`.sf-invite { bottom: 3.5rem }`）。Enter 是整个屏幕上唯一真正重要的目标——它是进站口——按当前设计它必须是"一个大目标"，因为手驱动的光标不是鼠标，第一次交互最不该做的事就是要求精度。
- 左下在内容页是 Home 返回区（正在改造成更大的渐变区域）。
- 右下目前空着，但把"高度控制"放在一个路人看不出用途的角落，等于没有。

更根本的问题：这是**给路人的一屏，说明只有一行字**。LOOK 已经要教一次"握拳抓住"。同一屏再教两个虚拟摇杆区，两个都会被忽略，而且它们会和 Enter 抢空间。

**决定**：第一版只做 LOOK。三轴平移移入 v2，前提条件写在这里，等 LOOK 在陌生用户身上验证过再谈：

- 版面前提：Enter 与 Home 的位置先定稿；移动区不得与二者重叠，也不得覆盖正文。
- 语义前提：v1 §4.3 的"抓取点即虚拟摇杆中心、抓取后可离开控件矩形不重新命中"是对的，照留。
- 方向前提：前后以**当前 yaw 的水平朝向**定义，世界竖直单独控制——照留，理由（抬头不该无意爬升）成立。

如果导师坚持第一版就要能"走进去"，退而求其次的方案是**把 dolly 挂在 LOOK 的同一次抓取上**：握拳后纵向位移不映射 pitch 而映射前后。这是一个自由度的取舍，不是新控件，成本极低——但要放弃"抬头看"，需要明确拍板。

### 2.4 网页点击 / 滚动 / Home

v1 §4.5–4.7 基本照留，逐条核对后的补充：

- **UI_PRESS**（§4.5）：✅ 与现状一致——tap 在释放时触发、丢手不算 tap、按压冻结坐标只用于点击目标。v1 说的"抓取开始时锁定目标"⚠️ **目前没有做**：`HandControl.click()` 是在释放时才 `elementFromPoint(pressAt)`，虽然用的是冻结坐标，但目标是那时才选的。改成抓取时锁定，是正确的收紧。
- **UI_SCROLL**（§4.6）：✅ 速度滚动、死区、`t²` 缓动、`canScroll` 判定全部与现状一致。v1 新增的"位移超阈后**永久**取消 click，即使移回中心也不再成为候选"⚠️ **现状不是这样**——`dragging` 一旦置位确实不再清除，但 `canScroll` 为假时仍会发出点击。v1 的收紧是对的，但要注意现状那条逻辑是为了修一个真实 bug（不可滚动页面上的小抖动导致"没点击、没滚动、没反馈"）。**两者都要满足**：不可滚动时给出"这里不能滚"的反馈，而不是退回发点击。
- **Home**（§4.7）：✅ 与正在进行的改造一致（Home 变成更大的渐变区）。v1 的三条约束全部照留，尤其"已有捕获时经过 Home 不触发、不抢夺"——这条在实现渐变大区域时极易漏掉，因为区域一大，飞行/滚动过程中扫过它的概率就高。

## 3 · 相机与滤波（修订）

### 3.1 ✅ 两套坐标，v1 说得对

UI 用已镜像、已限幅到屏幕的绝对光标；拖动用摄像头掌心位置 + 抓取瞬间冻结的尺度与原点。

⚠️ 一处必须点名：**拖动坐标不能用 `s.x/s.y`**。`mapToBox` 会 `clamp01`，手到了盒子边缘再往外移，`s.x` 就不动了——拖动会在屏幕边缘"消失"。而且 `s.x/s.y` 还带按压冻结（180ms），把冻结值当位移用会直接吞掉一段拖动。**必须新增一路未限幅、未冻结的抓取坐标**，`liveX/liveY` 也不够（它没冻结，但仍被 clamp）。这是 v1 §6.1 的正确直觉，落到本仓库是一个具体的新字段。

### 3.2 ✅ 环顾用位移，且基准已经存在

`deltaYaw = gainX * (handX - grabX)`，符号只定义一次。v1 §6.2 推荐的"相对抓取起点映射到抓取初始角度、不逐帧积分"——**`SparkCampusExperiment.tsx` 已经是这么写的**（`manual.offset` / `manual.yaw` 每帧从 `basePos`/`baseQuat` 重推，注释里写明"never from the previous frame's result, or the offset compounds and the camera runs away"）。改造只需把输入从量化方向换成连续位移。

### 3.3 移动与滚动用速度

v1 §6.3 的公式照留：

```
a = clamp((abs(d) - d0) / (d1 - d0), 0, 1)
v = sign(d) * vmax * a^gamma
```

✅ 与现有的 `dragScrollVelocity` 同构（那边 `gamma = 2`，`d0 = 0.025`，`d1 = 0.28`，`vmax = 2400 px/s`，且已在 78 条测试里被覆盖）。二维限幅、进出滞回照留。gamma 1.5–2 作为起点，🆕 并且**必须做成 URL 旋钮**。

### 3.4 ⚠️ 释放惯性：保留，但只在一种情况下触发

v1 §6.4 主张第一版关掉。**与导师明确提出的需求冲突**（"平滑减小，真实一点"、"扇一下"），所以不能照收。

但 v1 的担忧是真的：惯性最容易被拿来**掩盖语义冲突**——系统猜不出哪次是回位，就用惯性把抽搐糊过去。这正是要避免的。

**折中，且是可验证的折中**：

保留惯性，仅当**同时**满足以下四条才触发：

1. 这次操作是 LOOK（平移与页面滚动第一版无惯性——照 v1）；
2. 结束原因是**主动张手**，不是丢手、不是取消、不是进入 UI、不是超时；
3. 释放前 ~120ms 窗口内的位移**方向一致**（窗口内掉过头，按 0 速度释放）；
4. 速度超过一个明确的"扫动"下限——慢拖后松手不产生任何延续。

衰减为指数，时间常数约 0.8s，**总延续角度设硬上限**，并且下一次抓取立即清零。整体挂 `?fling=0` 可关。

这样"扇一下顺势转"成立，而 v1 担心的四种误触发一个都不会发生。**验收标准**（§6）里为此单列一条：慢拖释放的延续角度必须为 0。

### 3.5 ✅ 三种平滑分开调

v1 §6.4 的分层正确：观测滤波（One Euro，保留，用真实时间戳）/ 抓取中的相机跟随（先关掉多余层，测是否还需要很短的缓冲）/ 释放惯性（见上）。

⚠️ 补一条：本仓库的 `beta = 10` **不是抄来的**，是在归一化 0..1 单位下实测定出来的（论文默认 0.007 在这个单位下等于把自适应关掉；实测 4K 下快速横扫滞后 1299px vs 59px）。v1 "不复制其他项目的 beta"这条建议对本仓库已经满足，但**反过来也成立：我们的 10 不能被别的项目抄走**，它绑死在"输入是屏幕归一化坐标"这个前提上。

### 3.6 ✅ 推理频率与渲染频率必须解耦

v1 §6.5 正确，且比它以为的更要紧（见 §1.6）。落地要求：

- `HandPointer` 暴露一个**每个视觉帧自增一次的 `seq`**。抓取会话只在 `seq` 变化时累积位移增量——否则 60Hz 的渲染循环会把同一个 30Hz 的增量执行两遍，转速凭空翻倍。
- 速度型意图（滚动、将来的平移）可以在渲染循环按 `dt` 积分，但**必须带有效期**；超期立即归零。
- 切标签页回来或出现异常大的 `dt` 时重置，不补积分。现有代码已有 `Math.min(dt, 0.05)` 之类的护栏，但那是限幅不是重置。

### 3.7 ⚠️ 单一相机写入者：现状比 v1 以为的好

v1 §6.6 担心"导览、手势、惯性、重置各自改 `camera.position/quaternion`"。**实际上只有一个写入者**——`SparkCampusExperiment.tsx` 的那个 `tick`，导览分支与手动分支在同一个 tick 里互斥。

真正的问题不是多写入者，而是**交接状态只有 `manual.active` 一个布尔量 + 冻结的 `basePos/baseQuat`**：一次操作的归属、来源、结束原因都没有记录。所以 v1 §5 的"一次操作保存 ownerTrackId / operationKind / 结束原因"是对的，只是它该落在**手势会话**上，不是落在相机上。相机继续保持单写入者，不需要新建 CameraController 类。

✅ roam volume 与逐轴滑移保留。⚠️ `HAND_RANGE = 12` 的"距导览姿态 12 单位"限制：1 单位 ≈ 3 米，即 ~36 米，对第一版 LOOK（不平移）完全不构成约束，暂不动。等平移进来再按 v1 的建议换成固定的有效重建空间边界。

## 4 · 输入仲裁与状态机

v1 §5 的状态机✅ 采纳，删掉本版不做的两个分支：

```text
AUTOPLAY
  └─ 有效归属手 ──→ POINTING（光标出现，导览继续播）

POINTING
  ├─ 抓取落在可交互目标   ──→ UI_PRESS
  ├─ 抓取落在可滚动内容   ──→ SCROLL_PENDING
  └─ 抓取落在场景背景     ──→ LOOK
      〔v2: 移动区 → MOVE_XZ / 高度区 → MOVE_Y〕

UI_PRESS
  ├─ 主动张手且仍合格   ──→ 一次点击
  ├─ 位移足够且可滚动   ──→ UI_SCROLL（此后本次操作永不再点击）
  └─ 取消 / 丢手 / 归属歧义 ──→ 无点击

LOOK / UI_SCROLL
  ├─ 主动张手 ──→ POINTING（LOOK 满足 §3.4 四条则带惯性）
  └─ 丢手 / 帧过期 / 归属歧义 ──→ CANCELLED，立即停止
```

捕获优先级、一次操作的存档字段、`Unknown ≠ Open`、`TrackingLost ≠ Released`——全部照 v1，无修改。这几条是整份文档里最重要的部分，也是现状最欠缺的：`HandControl.tsx` 里确实有零散的每次操作状态（`pressAt` / `dragFrom` / `scrollEl` / `canScroll` / `dragging`），但没有归属、没有来源、没有结束原因，也没有一条统一的取消路径——所以"这次操作属于谁、该交给谁、为什么结束"每一帧都在重新推断。

## 6 · ⚠️ 验收：挂到真实的 harness 上

v1 §11 的门槛保留，但必须说清在哪里跑，否则没人会跑。仓库现有三个：

| 命令 | 是什么 | 本方案怎么用 |
|---|---|---|
| `npm run check:pointer` | 78 条离线测试，合成视觉结果 + 虚拟时钟驱动真实状态机 | **基线，改动后必须仍是全绿**。新增用例见下 |
| `npm run usertest:home` | 75 点覆盖网格，两种姿态，四条屏幕边缝 | 版面改动后跑 |
| `node scripts/vision-audit.mjs` | 离线指标；`--fixture` 跑归档数据 | pinch 消融用 |

🆕 必须新增到 `check:pointer` 的用例（每一条对应上文一个具体结论）：

1. **手消失后飞行意图当帧归零**——直接钉死 §1.1 那 1221ms，防止回归。
2. **握拳左右往返产生左右往返，不产生单向累积**——钉死 §2.2 的语义，防止有人再用惯性去糊。
3. **慢拖后主动张手，延续角度为 0**；**快速扫动后主动张手，延续角度 > 0 且不超过上限**——钉死 §3.4 的四条守卫。
4. **丢手结束的 LOOK 不产生任何延续**。
5. **一次操作跨越目标不改变接收者**（抓取时锁定，释放时不重选）。
6. **位移超阈后即使移回中心也不再点击**。
7. **同一个 `seq` 被消费两次不产生两倍转角**——钉死 §3.6。

v1 §11 表格里的数值门槛（停止性 p95 ≤ 200ms、跟随延迟 p95 < 150ms、点击首次成功率 ≥95%、意外导航 0 次、80% 新用户 60 秒内完成、性能同时报 p50/p95）✅ 全部保留，并保留 v1 自己的免责说明：**这些是待测门槛，不是已有实验结果**，必须结合基线调整。

⚠️ 补一条 v1 没有的：**每个门槛都要有配对的基线**。"改后 p95 是 180ms"没有意义，除非同时有"改前是多少"。现状的数字一个都还没测过。

## 7 · 实施顺序

v1 §10 的四阶段✅ 采纳，按本版结论重排：

**阶段 0 — P0 修复（不改任何交互）**
§1.1 手离开后继续飞、§1.2 三条应用层故障、§1.3 帧计数改毫秒、§1.6 只推理新解码帧。
退出条件：`check:pointer` 全绿 + 新增用例 1 通过；HUD 报出真实分辨率与推理帧率；离开画面后画面立即静止。

**阶段 A — 观测与归属**
`ObservationValidator` + `ActiveHandTracker`。临时、匿名、易失的轨迹匹配（掌心距离、尺度连续性、左右手标签作为线索而非 ID），活跃操作期间不换归属，歧义时停止而非强行切换。
退出条件：丢手、换手、跨控件拖动都不会触发意外导航。

**阶段 B — 相机数学先离线验证**
`GestureSession` + 连续位移驱动的 LOOK，用合成意图轨迹测。**在接手模型之前**，先证明相同输入在不同渲染/推理频率下产生相同结果。
退出条件：相机逻辑完全不依赖手势是否识别成功。

**阶段 C — 最小语法上线**
LOOK + 现有的点击与速度滚动 + 大 Home 区，全部走同一个状态机。dwell 保持关闭，惯性按 §3.4 的四条守卫开启。
退出条件：任何一次手势事务只能产生一种动作。

**阶段 D — 陌生用户测试与调参**
6–10 名未参与开发的志愿者，只看界面提示，完成"转身 / 停住 / 回 Home / 打开内容 / 向下滚动"。
对照组 A（现状：位置→定速）vs B（抓取位移 + 惯性），识别器、场景、距离尽量一致。
⚠️ v1 原文这里还包含"前进、升高"两个任务——本版第一版没有平移，任务表相应删减。
之后再依次测：更短的抓取确认、One Euro 调参、可选 pinch。最后才谈双手、选点飞行、物体 orbit。

**并行且独立 — pinch 消融**（v1 §7.2）
✅ 完整保留，一字不改：比较 `ratioWorld3D` / `ratioWorld2D` / `ratioPx`；`ratioPx` 必须用真实像素宽高；不预设 2D 更好，比较的是实际误报/漏报与首次成功率而非曲线形状；距离至少含 0.5m 对照与 1 / 1.5 / 2 / 2.5m；不要把 world-landmark 的 z 当作手到相机的绝对距离。
这条与相机改造**没有依赖关系**，可以并行，且它决定的是买哪台摄像头。

## 8 · 最小可交付版本（修订）

**必须包含**：稳定的临时手归属；单一输入管线；抓取会话捕获（一次操作一次捕获）；cancel 与 release 分离；**相对位移驱动的环顾**；页面点击与速度滚动；大而不重叠的 Home 区；失去有效观察即当帧停止；单一相机写入者；自动导览平顺交接。

## 9 · 这份文档没有解决的问题

诚实清单，避免它被当成比实际更确定的东西：

1. **所有性能与延迟数字都还没测过。** §6 的门槛是目标，不是结果。唯一有实测数字的是 §1.1 的 1221ms。
2. **距离仍未测量。** 归档里每一次试验都在 0.5m（见 `docs/vision-audit.md` §6），1–2.5m 区间没有任何数据。摄像头采购卡在这上面，本方案不改变这一点。
3. **"抓住场景拖动"的方向是猜的。** 拖动方向的正负号需要陌生用户测，不能靠开发者的直觉——开发者已经知道正确答案了。
4. **`?fling` 的三个参数（窗口、下限、上限）全是起点值**，必须在墙上调。
5. **平移一旦进来，pitch 限位、roam volume 边界、Enter/Home 版面三者会互相牵制**，本版只描述了约束，没有给出解。
